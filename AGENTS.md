# Study Vault project checks

- Flutter verification: `flutter test --no-pub`; target individual files for isolated changes. Run `flutter analyze` for Dart changes.
- POCO/ARM64 test APK: `flutter build apk --release --target-platform android-arm64 --split-per-abi --no-pub`. Output: `build/app/outputs/flutter-apk/app-arm64-v8a-release.apk`. The current Android release configuration uses the debug signing key, so this is a sideload/testing artifact, not a production-store release.
- Desktop layout: `DesktopFrame` (lib/core/widgets/desktop_frame.dart) wraps the root navigator with a persistent `NavigationRail` when `AppSpacing.isDesktopLayout` is true (Linux/Windows/macOS and window width ≥ 1000). Phones and narrow windows keep the mobile layout. Use `AppSpacing.contentWidth(context)` instead of the fixed 840 max width, and `AdaptiveItemList` for lists that should become grids on desktop. Tests: `test/desktop_layout_test.dart`.
- The desktop app stores SQLite and material files through `StudyVaultPaths`; do not change a live database while testing. Use `AppDatabase.forTesting(NativeDatabase.memory())`.
- `file-share-server/` is a separate unauthenticated LAN sharing tool, not the private cloud backend. Do not publish it as the authenticated API.
- `sync-server/` is the private Node/PostgreSQL backend. Production uses Node 24; its Dockerfile pins the runtime image.
- Install backend dependencies with `npm ci --prefix sync-server`.
- Backend integration tests: set `TEST_DATABASE_URL` to an isolated disposable PostgreSQL database, then run `npm test --prefix sync-server`. Tests create synthetic accounts and records; never target production.
- Build the backend with `docker build -t study-vault-sync:verification sync-server`.
- Additional checks: `npm audit --omit=dev --prefix sync-server`, `bash -n sync-server/deploy/backup.sh sync-server/deploy/renew-certificate.sh`, and `git diff --check`.
- Backend sync uses schema version 21, account-scoped rows, immutable revision history, explicit tombstones, mutation IDs for retries, and optimistic revision checks. Conflicting batches must remain atomic.
- The Flutter client checks `/v2/status`, fetches `/v2/changes?after=HEAD` (initial/upgrade load uses `/v2/snapshot`), and commits through `/v2/sync`: one account-wide expected head and a durable operation ID make a whole-library commit atomic and retryable. Do not replace this with independent v1 batches for related records.
- Sync is manual and opt-in. Its local baseline and pending operation are in `local_cloud_sync`, excluded from the synchronized app tables; account/server binding prevents accidental cross-account uploads. Never put session tokens in this table.
- The first implementation supports 20,000 metadata records, a 48 MiB snapshot, and files up to 256 MiB each. Conflicts require an explicit choice. Routine sync makes no full recovery archive. Device-local SQL triggers track changed rows in `local_cloud_sync_dirty` with a cursor/counter in `local_cloud_sync_cursor`; `local_cloud_sync_files` caches SHA-256 by size/modified/changed signature. These are not Drift/sync tables and need no schema bump. Temporary file replacements use a small `study_vault_sync_recovery/sync-staging` journal and SQLite apply marker; completed staging is removed, legacy recovery archives remain exportable from Settings.
- `test/cloud_schema_contract_test.dart` checks all 39 Drift tables against `sync-server/src/library-schema.json`. After an intentional database-schema change, regenerate with `flutter test --no-pub --dart-define=UPDATE_CLOUD_SCHEMA=true test/cloud_schema_contract_test.dart` and review the contract diff.
- Flutter sync checks: `flutter test --no-pub test/cloud_schema_contract_test.dart test/cloud_sync_merge_test.dart test/cloud_sync_service_test.dart test/cloud_account_test.dart`. With `TEST_DATABASE_URL` pointing at a local disposable PostgreSQL database, also run `flutter test --no-pub test/cloud_sync_http_test.dart` for a real Dart-to-Node-to-PostgreSQL round trip.
- The server's syncable table allowlist is derived from `sync-server/src/library-schema.json` (plus `material_files`); `store.js` refuses to start if that file's `schemaVersion` differs. After a schema bump, update `schemaVersion` in `store.js`, `kStudyVaultSchemaVersion`, `BackupService`, and the backend tests' batch helpers.
- Course Review (`lib/features/course_review/`): one complete Markdown document per subject, stored as the latest `course_review_entries` row with `part = document` and a null `material_id`. Each save appends a version. Older per-PDF `summary`/`explanation`/`deep_explanation` rows and subject-wide `examples`/`big_picture` rows stay readable and can be compiled into that document; they are no longer the editor. `course_review_exclusions` omit PDFs from the document fingerprint. The document is outdated when its `source_fingerprint` differs from the fingerprint of every included PDF and that PDF's current lesson-material or file fingerprint. Source changes never overwrite the document. The external prompt asks for one Markdown document. JSON import of the legacy `course_review` key still writes section rows. Tests: `test/course_review_test.dart`.
- Study Schedule (`lib/features/study_schedule/`): lesson-level spaced review. Setting a lesson to Reviewed/Mastered (`setLessonProgress`) auto-enrolls it; opening a lesson never does. `study_schedules` (one minimal row per lesson so offline double-enrolls merge as equivalent duplicates) + append-only `study_schedule_events` (start/review/reschedule; latest by `sequence_number` holds `due_on`). Days are `yyyy-MM-dd` text (`ScheduleDay`), never timestamps. `ReviewScheduler` is pure: ladder 1/3/7/21/60/120/240/365 days, Easy skips a rung, Hard ×1.2, Again → 1 day, late success credited for the real gap, early success never pulls a due date closer, exam cap = 40% of days left (`subjects.exam_date`; setting it pulls later reviews forward). Reviews sync lesson status (≥60-day success → mastered, Again → reviewed). Daily limit is a device-local SharedPreferences setting. Tests: `test/study_schedule_test.dart`, `test/study_schedule_screen_test.dart`.
- AI Generation Center (`lib/features/ai_generation_queue/`): device-local `local_ai_generation_jobs` table created in `beforeOpen` (not a Drift table, not synced, no schema bump). PDF Mental Blueprint, Summary, Explanation, Deep Explanation, Examples, and Slideshow jobs are queued FIFO with at most 2 running. The floating indicator and Generation Center stay above navigation. Partial New API output is stored on the job, not as a completed material. A killed process marks a running job `partial` or `interrupted`; it does not keep the provider request alive. System notifications are not available in this build. Each job stores the selected endpoint profile id and model id, never the API key. Deleting that profile marks queued jobs `configuration_required` instead of sending them through another profile. Tests: `test/ai_generation_queue_test.dart`.
- AI API profiles (`lib/features/ai_assistant/data/ai_endpoint_profile_repository.dart`): unlimited named API profiles, each using either the Anthropic Messages protocol (`/v1/messages`, New API/Claude gateways) or the OpenAI-compatible one (`/v1/chat/completions`, e.g. Dahl Inference). Both keep the same profile, key, and model picker; OpenAI-compatible profiles have no Anthropic `cache_control` or PDF attachments. Metadata and cached model ids live in device-local SharedPreferences (`ai_endpoint_profiles_v1`). Each key is stored only in `flutter_secure_storage` as `study_vault_ai_endpoint_key_<profileId>`. Profiles and keys do not sync and are not Drift tables. A custom model is an `AiModelRef` (`sv1:endpoint:<profileId>:<modelId>`), so two profiles with the same model id stay distinct. Legacy single New API URL/key/model migrates once into a profile named “New API”. Requests use the profile id captured on the selection, chat row, or queue job. Tests: `test/ai_endpoint_profile_test.dart`.
- AI caching: all pickers use the shared cached catalog (`ai_model_catalog_providers.dart`); expired custom lists refresh in the background with a 5-minute failure cooldown. Profile URL/key edits increment `connectionRevision`, clear discovery state, and invalidate in-flight discovery results; catalog mutations and connection resolution are serialized. `promptCachingEnabled` is a device-local per-profile opt-in for Anthropic `cache_control` (default off). Native API chats capture per-chat/model style in device-local SharedPreferences (`ai_chat_request_preferences_v1_…`); title requests are separate. `ChatHistoryPolicy` uses estimated-token/message high-water marks and deterministic batched extractive compaction, retaining the original source and latest question; excerpts are explicitly incomplete, and source overflow fails explicitly. Local annotation caching hashes the full effective request, profile revision, conversation, image bytes, and category mapping; partial output is never cached. Chat request diagnostics retain at most 100 metadata-only rows in device-local `ai_request_metrics_v1` (no prompts/keys, no sync, no schema bump). Tests: `test/ai_cache_regression_test.dart` plus existing AI profile/chat/annotation tests.
- Pocket chats (`AiProviderId.pocket`): ChatGPT, Claude, and Gemini in the local Pocket window (`http://127.0.0.1:8765`, model ids `sv1:pocket:chatgpt|claude|gemini`). No API key and no sync. Chat, study actions, quizzes, books, document generation, and Persian translation route there when that model is selected. Each request starts a new Pocket chat. Page images are temporary files attached to that request. Book embeddings stay on Gemini. Tests: `test/pocket_ai_test.dart`.
- Persian translations of AI study materials (`lib/features/pdf_ai_materials/`): `pdf_ai_material_translations` holds one row per source version + language (`fa`), FK-cascaded to `pdf_ai_materials`. Translations are section-aligned: `PdfAiTranslation.segments` (the reader's chunking) splits the original, each section is translated separately with code/formulas/charts/slide markers swapped for `⟦SVn⟧` placeholders, and the result is stored joined by `<!-- sv-segment -->` so section N ↔ section N. The reader's EN | فا toggle restores the same section after a switch (`_captureAnchor`/`_applyAnchor`); `source_hash` flags translations made before the original was edited. Code/chart/notation blocks are always rendered LTR. Tests: `test/pdf_ai_translation_test.dart`, `test/pdf_ai_translation_service_test.dart`, `test/pdf_ai_translation_reader_test.dart`.
- Reference books (`lib/features/reference_books/`): PDFs stored at `study_vault_files/books/{bookId}/{storedFileName}` (synced via `material_files`; `cloudFilePath` in `cloud_sync_models.dart` and the server's `validateLibrary` require the manifest). Synced tables: `reference_books`, `reference_book_subjects`, `reference_book_chapters`, `reference_book_ai_items` (versioned per book+kind+scope_key), `reference_book_notes`, `reference_book_messages`, `reference_book_links` (lecture PDF → page ranges), `reference_book_quizzes`. Device-local, non-Drift tables created in `beforeOpen`: `local_book_pages` (page text index), `local_book_vectors` (optional Gemini `gemini-embedding-001` @768 vectors), `local_book_state` (index progress, last page). Never make these Drift tables — they must stay out of sync. Search is pure-Dart BM25 (`BookTextIndex`) fused with cosine ranking when vectors exist. Extracted-text mode is the default: Ask sends ≤14 retrieved pages; long chapters are chunk-digested first. Native PDF mode is an explicit user choice: Ask can attach the whole book or the selected chapter; chapter/page actions attach only their requested range. Gemini accepts native PDFs; custom Anthropic-compatible profiles require device-local `pdfAttachmentsEnabled` and `pdfMaxPages` (default 100, configurable 1–600). Attachments are transient, ≤20 MiB, preserve original-page citation maps, and never store remote file IDs or PDF bytes in settings. DeepSeek and Pocket keep extracted-text mode; non-Gemini book requests never invoke Gemini query embeddings. Book model selection checks the chosen provider instead of the global default; cancelling never falls back to another model. Tests also include `test/book_ai_providers_test.dart` (real local PDF slicing plus mocked HTTP/provider routing). Lesson-PDF pins/bookmarks are FK-bound to `lesson_materials`, so books use their own reader and `reference_book_notes`. Tests: `test/reference_books_test.dart`.
- Lesson images: grid/list choice is device-local SharedPreferences (`lesson_images_grid_view_v1`). The image reader swipes left/right through image materials in the same lesson and material order, with previous/next controls and a counter. Single-pointer horizontal swipes navigate only at fit scale while annotation is off; zoomed panning, pinch gestures, and annotation never navigate. Active-image pins/favorites/discussions/review use the displayed material id. Async decode epochs reject stale image loads during fast navigation; missing files remain skippable. Tests: `test/image_gallery_test.dart` (temporary image files, in-memory database, mocked streams).
- Reader positions (`lib/core/storage/reading_positions.dart`): device-local numeric bookmarks in SharedPreferences (`study_vault_reading_position_v1_…`), keyed by library file path + resource + section/version/language. Synchronous memory saves plus serialized debounced writes preserve fast switches; no Drift tables, schema bump, study content, or sync. Markdown retains its keyed document subtree while opening the AI panel. PDF saves viewport center/zoom/page; explicit initial pages from search/bookmarks override saved positions. AI readers keep per-version/language offsets and section anchors, plus slideshow page, without accessing widget refs from dispose. HTML responses append a token-protected same-origin script that retains window and nested-element scroll in website localStorage; source files are unchanged. Tests: `test/reading_positions_test.dart`, `test/pdf_reader_position_test.dart`, `test/markdown_study_screen_test.dart`, `test/pdf_ai_material_test.dart`, `test/pdf_ai_translation_reader_test.dart`, `test/interactive_html_test.dart`; optional real browser check: `STUDY_VAULT_BROWSER_TESTS=true flutter test --no-pub test/html_reading_position_browser_test.dart` (Chrome, disposable profile).
- Interactive HTML (`lib/features/interactive_html/`): lesson materials with MIME `text/html` (one page, stored `<id>.html`) or `application/vnd.study-vault.html-bundle+zip` (a `.zip` with `index.html` plus its CSS/JS/images, stored `<id>.zip`). They are ordinary `lesson_materials` rows, so they sync through `material_files` with no schema bump; they are not documents, so AI materials, Course Review, and chat context ignore them. Opening a page unpacks it to the temp cache `study_vault_html/<materialId>/` (zip-slip rejected, ≤5000 entries, ≤512 MiB unpacked; imports ≤256 MiB) and serves only that folder from a loopback `HttpServer` with a per-open path token and a stable per-item port, so each page keeps its own `localStorage`. Android/iOS/macOS render in `webview_flutter` (cleartext allowed only for 127.0.0.1/localhost in `network_security_config.xml`); Linux opens a separate Python GTK WebKit2 4.1 window (`python3-gi`, `gir1.2-webkit2-4.1`; falls back to the browser) with device-local website data in `study_vault_html_webdata`; Windows uses the browser. Page-saved state never syncs. Remote references show a “Uses internet” badge. Tests: `test/interactive_html_test.dart`.
- Search (`lib/features/search/`): global search plus class/subject/lesson scopes, applied in SQL before limits. Each Search screen has an independent `SearchSession`; class, subject, lesson, notes, flashcards, and books have search entry points. `FileSearchIndexer` extracts PDF pages and overlapping Markdown/text sections locally, one file at a time, with streamed progress; it fingerprints material revision, storage identity, file size, and modification time, and removes failed/stale extraction. `local_search_files`, `local_search_pages`, and optional FTS5 `local_search_fts` + triggers are created in `beforeOpen`, never Drift/sync tables and no schema bump; literal LIKE works without FTS5. Only All/Materials searches initiate lesson-file indexing. Library material changes trigger rescans, and overlapping requests coalesce. Current AI material versions and Course Review documents are searchable directly; books search titles and existing `local_book_pages` (index a book in its reader first). PDF/book hits carry page numbers to readers; scanned PDFs need OCR and are reported as having no searchable text. HTML/images remain title-only. Tests: `test/file_search_test.dart`, `test/search_favorites_categories_test.dart`, `test/desktop_layout_test.dart`. Use temporary files and in-memory databases; never point tests at the live library.
- Termux agent access (`lib/features/agent_bridge/`): opt-in authenticated loopback bridge for the active phone library, plus the bundled stdio adapter `tool/study_vault_termux_mcp.py`. Settings starts a session with a random port/key (8-hour expiry), optional writes, and an Android foreground service. Stops on library scope disposal and before backup restore; sessions never persist/sync. No raw SQL/deletion/credentials tools. Writes preview unless `apply: true`; saves use Drift transactions and canonical codecs/versioning. Files are streamed through bounded authenticated endpoints, never a public folder. Setup/config instructions: `docs/termux-agent-access.md`. Tests: `test/agent_bridge_test.dart` (isolated memory DB and real Python-to-HTTP round trip).
- Devin MCP server: `tool/study_vault_mcp.py` (Python stdlib only, stdio JSON-RPC) reads and adds to the local SQLite library (`STUDY_VAULT_DB`, default `~/Documents/study_vault.sqlite`). Registered in `~/.config/devin/mcp_config.json` as `study-vault`. It never deletes study content; write tools preview unless `apply: true`. `add_lesson` and `attach_file` create lessons and copy local PDF/image files into `study_vault_files/lessons/` following the app's import invariants. It mirrors app invariants (unix-second timestamps, Quill delta via a port of `MarkdownToQuill`, Course Review fingerprints, version numbering), accepts only `SCHEMA_VERSIONS` — bump it with the app schema and re-run `test/study_vault_mcp_test.dart` (Dart ↔ Python round trip, sync-schema row validation). The app sets `busy_timeout` and `AppDatabase.watchExternalChanges()` (started in `databaseProvider`) polls `PRAGMA data_version` so open screens refresh after external writes.
- Drift live streams hang under widget-test fake time; in widget tests override stream providers with `Stream.value(...)` loaded via `tester.runAsync`.
- Private file manifests must reference an already-uploaded SHA-256-verified blob. Do not serve the file directory publicly.
- Production deployment uses the dedicated `/opt/study-vault` Docker Compose project. Do not alter other VPS projects, their credentials, or their databases.
- Keep database secrets and TLS private keys out of source control and terminal output. Provision the app account with the interactive `npm run account -- create USERNAME` command inside the API container.
- Server-side backups are retained without automatic deletion. The backup job refuses to start below 10 GiB free; arrange off-server backup storage separately.
